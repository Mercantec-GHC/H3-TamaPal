## GitHub-workflow (anbefaling fra underviserne)

- **Issues + Projects** er et "løst krav", men stærkt anbefalet. Underviserne kan se historikken:
  hvem har lavet hvad, og hvad vi har aftalt.
- **Issue** = titel + beskrivelse + **acceptkriterier** ("Hvornår er det her færdigt?").
  Eneste faste regel: læs acceptkriterierne igennem, før du siger "færdig".
- **Assignee**: hvert Issue har én ansvarlig. Labels, prioritet og estimater er frivillige.
- **Board**: kanban med status. Konkrete kolonner blev ikke nævnt.
- **Branches**: lav en branch ud fra et Issue med præfikset `feature` (fx `feature/pong-canvas`).
- **Pull Request**: link til Issuet, beskriv hvad der er lavet i forhold til acceptkriterierne.
  En anden læser koden og godkender – helst 2 godkendelser.
- **Beskyttet `main`**: der kommer ikke kode ind uden godkendt Pull Request.
- AI (fx Copilot) må gerne skrive beskrivelser til Issues, hvis gruppen er enig.

## Krav til mellemprojektet (Definition of Done)

1. Mini-GDD (ca. 10 punkter).
2. Tydeligt gameplay loop, og spillet kan startes, spilles og afsluttes.
3. Oplàen er controller med mindst **2 forskellige handlinger**.
4. Kommunikation Arduino → backend med en protokol, vi kan forklare.
5. Backend styrer spillets tilstand og mindst én del af logikken (point, liv, regler).
6. Frontend viser tilstanden og giver feedback.
7. Arduino, backend og frontend virker sammen.
8. **Brugertest** med mindst én person uden for gruppen + mindst én forbedring.
9. Koden ligger på GitHub, og alle har bidraget.

Nice to have: MQTT, multiplayer/lobby, SignalR/WebSocket, sværhedsgrader, lyd og animationer,
highscore i database, deployment. JWT/login er **ikke** et krav i dette projekt.
Til database blev **Neon** (PostgreSQL) anbefalet.

### Sådan arbejder vi

1. Tag et Issue fra tavlen, sæt dig selv som assignee, flyt det til **In progress**.
2. `git switch dev` → `git pull`.
3. Færdig → commit → `git pull` → `git push` direkte til `dev`. Skriv `Closes #<nr>` i commit-beskeden.
   Ingen Pull Request eller review til `dev` (aftalt i gruppen 4/11). En `feature/<navn>`-branch med PR er valgfri.
4. Release: Pull Request `dev` → `main`, godkendes, tag (fx `v0.1.0`).
